# Feature map

This map lists the supported product features, where each one starts, which code owns its data, and how each one is verified today. It describes `main` after PR #46, with the verification added for issue #31 and the onboarding change.

Update this file in the same pull request when you add, remove or change a route, an entry point, a user flow, a server module or the verification of a feature.

Template leftovers: the demo routes and demo data were removed before issue #33. Issue #33 removed the unused template assets (`src/logo.svg`, `public/demo-neon.svg`, `public/drizzle.svg`, the TanStack logos, and `public/manifest.json` with its icons, which no page linked). Issue #20 replaced the starter `public/favicon.ico`. `src/integrations/tanstack-query/` stays: the router and the root layout use it.

## How to read the verification column

- **Unit**: runs in `npm run test` with no database. It always runs in CI through `npm run quality`.
- **DB (optional)**: runs only when its environment variable points to a disposable local PostgreSQL database. Without the variable, Vitest skips it. CI does not set these variables, so CI skips them.
  - `INTEGRATION_TEST_DATABASE_URL` → `src/test/feature-integration.test.ts` (cross-feature: risk, imports, reviews, account isolation).
  - `IMPORT_TEST_DATABASE_URL` → `src/test/import-sql.integration.test.ts`.
  - `REVIEW_TEST_DATABASE_URL` → `src/test/review-database.test.ts`.
  - `TAGS_TEST_DATABASE_URL` → `src/test/trade-tags.integration.test.ts`. It accepts any local `jottrade_test_*` database (the `npm run db:check` rules) and drops its schema.
  - `SCOPE_TEST_DATABASE_URL` → `src/test/analysis-scope.integration.test.ts`. The same rules as `TAGS_TEST_DATABASE_URL`.
  - Gap: the fixtures accept only `127.0.0.1` with fixed ports, users and database names (for example port `49485`, database `integration_behavior`). They do not accept the `jottrade_test_*` databases that `npm run db:reset` creates ([development-database.md](development-database.md)), so `npm run verify` does not run them.
- **DB (verify)**: `src/test/user-isolation.integration.test.ts`. `npm run verify` runs it on a fresh, seeded `jottrade_test_*` database through the real `@/db` client. CI runs it in the **E2E** check. Without `VERIFY_DATABASE_URL`, Vitest skips it.
- **E2E**: a Playwright spec in `e2e/`. `npm run verify` runs the suite against the production build and the seeded database. CI runs it in the **E2E** check. See [quality-gate.md](quality-gate.md), section "Critical-flow verification".
- **Gap**: no automated check exists.

To run one file: `npx vitest run src/test/<file>`.

## Features

### Authentication

- **Entry**: `/sign-in`, `/sign-up`, `/forgot-password` ("Forgot password?" on `/sign-in`), `/reset-password` (the email link); protected routes redirect to `/sign-in`.
- **Flows**: email/password sign-up and sign-in; Google sign-in (`authClient.signIn.social`). Password reset: the request page always shows the same message; the email link expires after 1 hour and works one time; a reset signs out all sessions. The reset request has a limit of 3 per 60 s for each client IP. A reset for a Google-only user adds a password to the account. Sign-out (sidebar and bottom nav, `src/hooks/use-sign-out.ts`, `sign-out-dialog.tsx`): when the user has trade or review drafts on this device, a dialog says "N drafts on this device are not in your journal. Signing out deletes them." "Cancel" has the focus. "Delete drafts and sign out" sends the sign-out request. Only when it succeeds, the app deletes only this user's draft keys (`clearUserDrafts` in `src/lib/review-draft.ts`), goes to `/sign-in` and clears the TanStack Query cache. When it fails, the drafts and the session stay, and a toast says "Couldn't sign out. Your drafts are kept. Try again." With no drafts, sign-out has no dialog. A session that expires keeps the drafts for the same user.
- **Code**: `src/lib/auth.ts` (server, Drizzle adapter), `src/lib/auth-client.ts`, `src/routes/api/auth/$.ts`. Server functions use `authMiddleware` (`src/server/auth-middleware.ts`), which calls `requireUserId()` and puts `userId` in the handler context. A Better Auth `user.create.after` hook gives each new user a default account (`ensureDefaultPortfolio` in `src/db/portfolios.ts`). Reset emails: `src/lib/email.ts` (server-only, Resend HTTP API; `RESEND_API_KEY`, `EMAIL_FROM`). Password rules: `src/lib/password.ts`.
- **Data**: `user`, `session`, `account` (OAuth link, not a trading account), `verification` in `src/db/trading-schema.ts`. Better Auth owns them.
- **Verification**: E2E `auth.spec.ts` (redirect of a signed-out visitor, sign-in that survives a reload, wrong password, another user's trade URL shows "Journal entry not found"; sign-out with a draft warns with "Cancel" focused, deletes the draft, and the next user on the same browser sees no draft; offline trade notes show "Offline. Saved on this device only." and save on reconnect, and a newer edit from a second browser gives the conflict choice). Unit `sign-out.test.tsx` (no dialog with no drafts; the dialog, then delete and sign-out; "Cancel" keeps the drafts; the query cache is empty; a failed or offline sign-out keeps the drafts, the session and the cache), `review-draft.test.ts` (`clearUserDrafts` keeps the keys of other users and the theme). E2E `server-auth.spec.ts` (a captured server-function read and write, replayed over HTTP with no session and with another user's session, fail). DB (verify) `user-isolation.integration.test.ts` (no session: reads and writes fail with "Unauthorized" before the handler). Unit `server-boundaries.test.ts` (every server function uses `authMiddleware`). Unit `email.test.ts` (production without a key or sender fails and logs no link), `password-forms.test.tsx` (the same message for each email, password rules, an expired or used link). DB (verify) `password-recovery.integration.test.ts` (the same response for an unknown and a known email, a 1-hour token, a token works one time, an expired token fails, a password change needs the current password, a Google-only user gets no credential change). E2E `password.spec.ts` (reset with the emailed link, then sign in; a used link; the rate limit; a change on the profile page signs out another device). Gap: sign-up in the browser and Google sign-in. DB (optional) `feature-integration.test.ts` and `review-database.test.ts` reject foreign users and unauthenticated calls.

### Trading accounts

- **Entry**: Settings → Trading accounts (`src/components/settings/TradingAccounts.tsx`); account switcher.
- **Flows**: create and edit an account (real/demo kind, description, reporting currency); delete with a typed-name confirmation; switch the active account. Every journal, dashboard, calendar, strategy and review query reads the active account.
- **Server**: `src/server/portfolioActions.ts` (`getAccounts`, `ensureDefaultAccount`, `createAccount`, `updateAccount`, `deleteAccount`). `getAccounts` only reads. Sign-up provisions the default account. For a user without a default account (signed up before the hook, or deleted the default), `useAccounts` calls the idempotent POST `ensureDefaultAccount`, which creates "Main account" or marks the oldest account as the default.
- **Data**: `portfolios`; queries in `src/db/portfolios.ts`.
- **Verification**: Unit `delete-account-dialog.test.tsx`, `app-sidebar.test.tsx`. DB (optional) `review-database.test.ts` (account deletion cascades review links), `feature-integration.test.ts` (account isolation). DB (verify) `user-isolation.integration.test.ts` (another user cannot read, edit or delete an account; `getAccounts` does not write; five concurrent `ensureDefaultAccount` calls create one default; a missing default is repaired once). DB (verify) `sign-up-provisioning.integration.test.ts` (sign-up through the real Better Auth instance creates the default account). E2E `accounts.spec.ts` (switch the account; the journal follows and the choice survives a reload). Gap: create and edit.

### First-run onboarding (issue #14)

- **Entry**: the checklist card at the top of `/dashboard` (`src/components/onboarding/onboarding-checklist.tsx`). Settings → "Setup guide" shows it again after a dismissal.
- **Flows**: four steps, each derived from real data: account set up (a review timezone is saved, or the user has a trade), opening deposit recorded, first trade added, first daily review completed. Each step links to the screen that does the work; "Set up account" opens `first-account-dialog.tsx` (name, broker, currency, timezone). The card hides itself when all steps are done or when the user dismisses it. It does not use `getAccounts`. The broker is stored in the account description. Logic in `src/lib/onboarding.ts`.
- **Data**: reads `portfolios`, `cash_flows`, `trades`, `review_periods`. Writes `user_onboarding` (only the dismissal time) and, in `setupFirstAccount`, `portfolios`.
- **Verification**: Unit `onboarding.test.ts` (step derivation and input schema), `onboarding-checklist.test.tsx`. E2E `onboarding.spec.ts` (Nora sets up the account from the checklist and sees 1 of 4 steps done, also after a reload). DB (optional) `onboarding-actions.test.ts` with `ONBOARDING_TEST_DATABASE_URL` set to any local database; it uses temporary tables and leaves real tables unchanged. Unsupported import data gets specific guidance: see "Imports with reconciled batches and undo". Gap: sample data is not built (owner decision).

### Journal (manual trades, funding and adjustments)

- **Entry**: `/journal`; "Log trade" drawer (`log-trade-drawer.tsx`, also `/journal?intent=log`); command palette "Log trade"; row click → `/journal/$tradeId`.
- **Flows**:
  - Filter by symbol, side, status, strategy, confidence, mistake, tags and period; page through results. Tabs: All entries, Trades, Adjustments, Funding.
  - Log a trade (`TradeEntryForm.tsx`), edit it and delete it from the detail page (`TradeDetailSheet.tsx`, `DeleteTradeDialog.tsx`).
  - Choose a strategy when you log a trade: the select lists active strategies, and "Show playbook" opens its criteria and risk guidance for reference (`playbook-summary.tsx`). With no strategies, the select shows "No strategies yet" and a link to `/strategies`. The detail page lists active strategies and the current archived one, as "Name (archived)".
  - Strategy rule: `createTrade`, and `updateTrade` when `setupId` changes, accept only an active strategy of the user (`requireOwnedStrategy` in `src/db/strategies.ts`). An unchanged archived strategy still saves. The write locks the account row first, as `deleteStrategy` does, so a save cannot link a strategy that a concurrent delete removed.
  - Retry rule: `createTrade` accepts an optional `clientDraftId` (UUID) and returns `{ success, id, duplicate }`. A second call with the same id from the same user returns the first trade with `duplicate: true` and inserts nothing (partial unique index `trades_user_client_draft_unique` on `(user_id, client_draft_id)`). The same id from another user makes a new trade. The archive export leaves `client_draft_id` out.
  - Local draft for "Log trade" (`src/lib/trade-draft.ts`, `src/hooks/use-trade-draft.ts`, `trade-draft-notice.tsx`): the form writes its values to `localStorage` 500 ms after each change, under `jottrade.trade-draft.v1:<user id>:<account id>`, with a `draftId`. The draft keeps the account of the form. Each account shows only its own draft, and the "Log Trade" button shows "Draft" when the active account has one. The form shows "Draft on this device. Not in your journal yet." and the time of the last change, with "Discard draft" (with a confirmation). Cancel and close keep the draft. A draft expires after 30 days with no change. A value that does not parse stays and shows "This draft cannot be read. Discard it." A prefilled form (setup calculator) asks "Continue your draft" or "Start new" when a draft exists. A restored strategy that is archived or gone is removed. The draft never saves on its own: "Log" sends the `draftId` as `clientDraftId`, so a retry after a lost response makes one trade. A failure shows "Not saved. Your draft stays on this device." A save deletes the draft and shows "Trade saved to journal". Account delete deletes the account's draft.
  - Edit rules: a blank optional price, rate or fee is stored as "no value" (blank fees as 0), so an open trade stays open with no P&L. A closed trade cannot clear its exit price; enter the corrected exit price instead (`src/lib/trade-update.ts`).
  - Add, edit and delete deposits, withdrawals and adjustments (`AccountEntriesPanel.tsx`, `account-entry-form.tsx`).
  - Upload and delete trade screenshots (`trade-images.tsx`). This needs the `GCP_*` variables (`src/lib/gcp.ts`). The server names each object `trades/<user id>/<trade id>/<upload id>.<ext>`; it does not use the file name. Each selected file shows "Uploading", then the thumbnail, or "Failed: <message>" with "Retry" and "Remove". A retry uses the same upload id, and `saveTradeImage` returns `alreadyAttached` for a URL that is already on the trade, so a retry makes no second object and no second entry. The delete button shows on touch screens, on narrow screens and on keyboard focus.
  - The detail page shows price return and account return (`trade-returns.tsx`).
- **Server**: `getTrades.ts` (`getTrades`, `getTradeById`), `tradeActions.ts` (`createTrade`, `updateTrade`, `deleteTrade`), `cashFlowActions.ts`, `imageActions.ts`.
- **Data**: `trades`, `cash_flows` (`cashFlows`).
- **Verification**: Unit `journal-table.test.tsx`, `journal-entries.test.ts`, `filter-bar.test.tsx`, `delete-trade-dialog.test.tsx`, `trade-returns.test.tsx`, `finance.test.ts`, `instruments.test.ts`, `date.test.ts`, `period.test.ts`, `trade-target.test.ts`, `trade-blank-decimals.test.ts` (blank fields, the closed-trade exit rule and the strategy rule, through `createTrade` and `updateTrade` with a mocked database). E2E `trades.spec.ts` (create a strategy, log a trade with it and see its playbook, edit and delete the trade; each change survives a reload; at 375 × 812, a draft survives a reload, and a lost response and a retry make one trade; each account shows only its own draft). Unit `trade-draft.test.ts` (key, expiry, unreadable value kept), `trade-entry-form.test.tsx` (restore, fixed account, failure keeps the draft, same `draftId` on retry, discard, archived strategy, prefill choice). DB (verify) `user-isolation.integration.test.ts` (another user cannot read, create, edit, move or delete trades and cash flows), `strategy-isolation.integration.test.ts` (another user's strategy is refused on a trade create, edit or bulk edit; an archived strategy stays on its trade and is refused on a new assignment), `trade-create-idempotency.integration.test.ts` (the retry rule). Unit `trade-images.test.tsx` (a failed upload shows "Failed" and "Retry"; a retry sends the same upload id; two files named `image.jpg` get two upload ids). DB (verify) `trade-images.integration.test.ts` (object names come from the upload id; a second save of one URL keeps one entry; another user cannot attach a URL under the first user's prefix). Gap: screenshot upload in the browser (verify has no GCP bucket); funding and adjustment entries in the browser.

### Risk and discipline rules (issue #19)

- **Entry**: Settings → "Risk and discipline rules" (`src/components/settings/risk-rules-settings.tsx`), for the active account. The entry preview (`src/components/journal/rule-check-preview.tsx`) shows under the risk preview in the "Log trade" form and in the command palette trade confirmation. The trade detail shows "Rule check at entry" (`src/components/journal/trade-rule-check.tsx`) in the original risk plan section.
- **Flows** (slice A): set, edit and clear four optional limits: max risk per trade (an amount in the account currency, a % of the balance at entry, or both), a daily loss limit (an amount, or a % of the day-start balance), max trades per day, and a cooldown (wait M minutes after N losing trades in a row). Each save that changes the rules or the review timezone makes the next version; a save with no change (decimals compare in one canonical form) writes nothing and shows "No change. Nothing was saved." "Clear rules" saves a version with no limits. Old versions do not change. A version starts at its save time (no backfill), and its days end at midnight in the review timezone saved with it. The footer shows the version, the start time and the timezone. When the review timezone changed after the save, a notice asks for a new save. With no review timezone, the section shows "Choose your review timezone first." The disclaimer (`RULES_DISCLAIMER`) says the checks are reminders. Rules are advisory only.
- **Flows** (slice B): the entry preview checks the trade against the version in effect at the entry time (the latest version with `effective_from` at or before the entry). It shows one row per set rule with an icon and a text status (Pass, Violated or Unknown), then the account, the day, the timezone, the version and the disclaimer. A violation does not block "Log". With no version, the preview shows "No rules for this account." and a "Set rules" link. When the context read fails, it shows "Could not check rules. You can still log the trade." and "Retry". Rules: risk per trade compares the initial risk amount or % (rounded to 2 decimals) with the limit; a missing stop, FX rate, spec or balance, or a plan in another currency, gives Unknown, never Pass. Daily loss is the realized net loss of closed trades on the entry day before the entry, plus the trade itself when it is logged closed on that day; it is Violated when it reaches the limit and Unknown when a closed trade of the day has no P&L. A % limit uses the day-start balance: deposits, withdrawals, adjustments and realized P&L before midnight, with the dashboard balance function (`summarizeTrades`). The balance is Unknown when it is not positive or an earlier closed trade has no P&L. Trades per day counts the trades entered on that day plus this trade. Cooldown is Violated before the end of the wait after the last N losing trades in a row, and Unknown when one of them has no exit time or no P&L. Days end at midnight in the version timezone.
- **Flows** (slice C): `createTrade` runs `evaluateEntry` on the server with the plan and the P&L that it inserts, and stores the result on the trade. This stored check is the truth: when it differs from the preview (for example, after a save in another tab), the form and the command palette show a toast with the stored result. When one or more rules are Violated, the preview shows "Why did you take it? (optional)" (max 500 characters); the local draft keeps the note. The save is never blocked; a trade with a violation stores `acknowledged: true` and the note. With no version in effect, the trade stores no check. When the rules cannot be read, the save continues and stores Unknown, "Rules could not be read". A retry with the same `clientDraftId` returns the stored check of the first trade. `updateTrade`, risk corrections, bulk edits and imports do not write the check. The detail panel shows "Logged before rules, or imported." when there is no check; else the stored outcomes, the version, the day, the note and the disclaimer.
- **Flows** (slice D): the dashboard shows "Rules today" (`src/components/dashboard/rules-today-card.tsx`) under the account summary: the loss left today ("Realized only"), the trades left, the cooldown end, and the open initial risk with the count of open trades with unknown risk. The heading shows the account, the day, the timezone and the version. With no rules, it shows "No rules for this account." and "Set rules". "Rule compliance" (`rules-compliance-section.tsx`) shows for the period one row per rule (checked, pass, violated and unknown counts), then the violations, newest first, 20 per page with "Show more". Each violation links to its source trades (`/journal/$tradeId`); a daily loss violation also links to the closed trades of that day in the journal. Imported trades have an "Imported" badge. Empty: "No violations in this period." A trade attribute filter shows "Rules use the account and the period only." The footer shows the account, the timezones and the versions used. Both surfaces show the disclaimer, a loading state and an error with "Retry". Definitions: [metrics.md](metrics.md), "Rule compliance".
- **Server**: `src/server/riskRuleActions.ts` (`getRiskRules`, `saveRiskRules`, `clearRiskRules`). SQL in `src/db/risk-rules.ts`: a user-scoped account read, then one insert under the account lock that computes the next version and skips a save with no change. Rules document: `riskRulesInputSchema` and `storedRiskRulesSchema` (`v: 1`) in `src/lib/risk-rules.ts`. `getRuleContext({ portfolioId, entryDate })` (`src/db/risk-rule-context.ts`) reads the owned account, its versions, trades and cash flows, and returns the day facts from `buildRuleContext`. `evaluateEntry` in `src/lib/risk-rule-evaluation.ts` is pure, so the server can run the same check. Query key `QueryKey.RuleContext`, invalidated after trade and account entry changes. `getRuleToday({ portfolioId })` and `getRuleCompliance(analysisScope)` (`src/db/risk-rule-compliance.ts`) read the owned account, all its versions, trades and cash flows, then run the pure `evaluateToday` and `evaluateCompliance` (`src/lib/risk-rule-compliance.ts`). Query keys `QueryKey.RuleToday` and `QueryKey.RuleCompliance`, invalidated after trade, account entry and rules changes.
- **Data**: `risk_rule_versions` (append-only; unique `(portfolio_id, version)`; account and user delete cascade) in `src/db/risk-rule-schema.ts`; nullable `trades.rule_check` (`ruleCheckSchema`, `v: 1`, in `src/lib/risk-rule-evaluation.ts`: version, timezone, day, evaluation time, capture source, outcomes, `acknowledged`, note, reason), written only by `createTrade`. Migration `drizzle/0014_risk_rules.sql`. The full archive includes `riskRuleVersions`.
- **Verification**: Unit `risk-rules.test.ts` (limits, one or more rules, canonical decimal strings), `risk-rules-settings.test.tsx` (no timezone, empty, version footer, timezone notice, save, no change, invalid, server error, clear). DB (verify) `risk-rules.integration.test.ts` (versions 1 to 3 with the first row unchanged, no write for a save with no change, no timezone, another user cannot read, save or clear, "500" and "500.00" are no change, account delete removes the versions), `account-deletion.integration.test.ts` (user delete). E2E `risk-rules.spec.ts` at 375 x 812 (a new user saves versions 1 and 2; the values and the disclaimer stay after a reload).
